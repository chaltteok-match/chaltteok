# 평가 요구사항

주최측이 공지와 질의응답으로 밝힌 내용이다. 추측은 적지 않는다.
「예정」은 변경 가능성이 있다고 주최측이 밝힌 것, 「미정」은 아직 답이 없는 것이다.

마지막 확인: 2026-09-04

## 0. 날짜

| 시각 | 일 |
| --- | --- |
| 2026-09-06(일) 23:59 | **제출 마감.** 이후 결과물 수정 금지 |
| 2026-09-07(월) 10:00 | 평가 서버 운영 시작. 이때 우리 서버가 떠 있어야 한다 |
| 2026-09-11(금) 15:00 | 평가 서버 운영 종료 |

운영 기간은 **4일 5시간**이다. 이 기간에 참가팀 답변 수집이 순차적으로 진행된다.
언제 우리 차례가 오는지는 알려주지 않으므로 기간 내내 켜 두어야 한다.

마감과 운영 시작 사이가 10시간뿐이다. **배포는 마감 전에 끝내 둔다.**
서버 구성은 코드 수정이 아니지만, 마감 뒤에 문제를 발견해도 코드로 고칠 수 없다.

## 1. 제출

| 항목 | 내용 |
| --- | --- |
| 마감 | 2026-09-06(일) 23:59 KST |
| 방법 | 대회 저장소에 **push**. Endpoint URL은 **README.md에 명시(필수)** |
| 제출물 | Endpoint URL, 전처리 산출물, 재현 가능한 환경 구성 정보, 기술제안서 |

- 대회 저장소는 `miraeasset-aifestival-2026-dart/dis-055`다. 작업은 우리 저장소
  (`chaltteok-match/chaltteok`)에서 하고 완료 후 옮긴다.
- **제출 기한 후 결과물 수정은 엄격히 금지**된다. 제출한 코드를 검증하는 작업이 평가 과정에
  포함될 수 있다.
- 전처리 산출물도 제출 대상이다. 대용량이면 클라우드 스토리지 링크로 대체할 수 있다.
- Dockerfile은 필수가 아니다. 단 `requirements.txt` 등 재현 가능한 환경 구성 정보는 제출해야 한다.
- 기술제안서에 분량·양식 제한은 없다.
- 이전 공지에는 구글폼으로 Endpoint URL을 낸다고 되어 있었다. 최신 공지는 push와 README 명시를
  요구한다. 둘 다 한다.

## 2. 평가 호출

| 항목 | 값 | 상태 |
| --- | --- | --- |
| 호출 방식 | sequential. 질의가 한 건씩 순서대로 들어온다. 동시 요청 없음 | 확정 |
| 응답 타임아웃 | 300초 | 확정 |
| 재시도 | **타임아웃 또는 5xx** 발생 시 최대 2회 | 확정 |

### 요청

```
GET {team-end-point}/answer?question_id={질의 ID}&question={평가 질의}
```

- 경로는 `/answer`로 **고정**이다.
- 요청에 **별도 헤더를 쓰지 않는다.** 인증 헤더도 없다.
- 접근 제어가 필요하면 주최측 발신 IP 허용 방식을 쓴다.

### 응답

```json
{
  "question_id": "Q-001",
  "question": "평가 질의 원문",
  "retrieved_context": "답변 생성에 참고한 검색 문서",
  "think_trace": "사고, 추론, 도구 사용 과정",
  "answer": "최종 생성 답변"
}
```

- 모든 필드가 **string 타입**이어야 한다. 빈 문자열 반환은 문제되지 않는다.
- `Content-Type`은 `application/json`으로 반환한다.
- `retrieved_context`에 문서가 여럿이면 문자열 안에서 구분 태그로 자유롭게 잇는다.
  **어떤 구분 태그를 쓰는지는 평가 대상이 아니다.** `think_trace`의 형식 규정도 없다.
- 필드 길이 제한은 없다. 단 극단적으로 길어 평가 시스템의 처리 분량을 넘기면 초과분이
  평가에 반영되지 않을 수 있다.
- 제공 코퍼스로 답할 수 없는 질의가 섞여 들어온다. 「정보한계대응」이 평가 항목이다.

## 3. 서버 구성

**HTTPS도 도메인도 필요 없다.** 공인 IP 하나면 된다.

| 항목 | 내용 |
| --- | --- |
| 프로토콜 | **HTTP 기본.** HTTPS를 써도 되고, 그 경우 자체 서명 인증서도 무방 |
| 포트 | HTTP는 **80**, HTTPS는 443. 표준 포트를 쓴다 |
| 도메인 | **준비할 필요 없다.** 외부 접속 가능한 공인 IP로 제출하면 된다 |
| 네트워크 | Public 망에서 접근 가능한 구성은 **필수** |
| 서버 환경 | 자유. 네이버클라우드도 개인 서버도 된다 |

- 주최측 **발신 IP 대역은 추후 공지 예정**이다. 나오기 전까지 방화벽을 좁히지 않는다.
  대역이 공지되면 그때 그 대역만 열도록 좁힐 수 있다.
- 개인용 환경(노트북 등)으로 구성해도 된다. 이 경우 외부 접근 가능한 **정적 도메인 URL**을
  내고, `ngrok` 같은 터널링 서비스를 자유롭게 쓸 수 있다. 다만 나흘을 켜 두어야 하므로
  본안으로는 부적합하고 배포가 막혔을 때의 대비책이다.
- 장애 등으로 서버를 다시 띄우는 것은 실격 사유가 아니다.
  **제출 결과물을 바꿀 목적이 아닐 때에 한한다.**

## 4. 저장소와 CI

- 대회 Organization의 GitHub Actions는 비활성화되었다. push·pull·clone·PR은 그대로 쓸 수 있고,
  Actions 사용 여부는 평가에 영향이 없다. CI가 필요하면 로컬이나 네이버클라우드에서 돌린다.
- 저장소 deploy key 등록은 조직 정책으로 막혀 있다. 대신 fine-grained PAT을 쓴다.

### fine-grained PAT

서버가 저장소 코드를 내려받으려면 인증 수단이 필요하다. 계정 비밀번호 대신 쓰는, 범위를 좁힌 열쇠다.

**대회 저장소용 PAT은 필요 없다.** 서버가 내려받아 실행할 코드는 우리 저장소
`chaltteok-match/chaltteok`에 있고, 대회 저장소에는 마감 때 우리가 push해 넣을 뿐이다.
그 push는 서버가 아니라 각자 노트북에서 평소 GitHub 로그인으로 한다.

발급 경로는 GitHub `Settings → Developer settings → Fine-grained tokens`이다.

| 항목 | 지정할 값 |
| --- | --- |
| Resource owner | **`chaltteok-match`** (대회 organization 아님) |
| Repository | `chaltteok-match/chaltteok` |
| Permissions | Contents: Read-only |

`Read-only`이므로 이 토큰으로는 코드를 읽기만 하고 밀어 넣을 수 없다. 서버가 털려도 저장소가
훼손되지 않는다.

`chaltteok-match`는 우리 organization이고 예령이 admin이라 **승인을 직접 할 수 있다.**
대회 organization으로 발급하면 주최측 관리자 승인을 기다려야 하는데, 그럴 이유가 없다.

## 5. 비용

- 제공 크레딧은 부가세를 포함하며 네이버클라우드 자원 전반에 적용된다. 서버·네트워크·CLOVA Studio가
  모두 같은 크레딧에서 빠진다.
- 주최측의 별도 비용 보전은 없다.
- 서버를 09-07 10:00부터 09-11 15:00까지 **나흘 남짓 켜 두어야** 한다. 배포 전에 잔여 크레딧이
  그 기간을 감당하는지 확인한다.
- 잔여 크레딧은 `ncloud.com > 마이페이지 > 결제 관리 > 크레딧 및 할인 관리 > 콘솔`에서 확인한다.

## 7. 기술 제약

### LLM 모델 제한

하이퍼클로바를 **써야 하는 범위가 다음으로 한정**된다.

- 답변 생성 LLM
- Multi-agent 또는 Agent workflow를 구현할 경우, 해당 Agent의 LLM

즉 **전처리·임베딩·리랭커는 제한 밖**이다. 우리 파서는 전부 규칙 기반이라 지금 달라지는 것은
없지만, 검색 품질이 문제가 되면 임베딩을 얹을 길이 열려 있다.

### 그 밖

- 형태소 분석기, 규칙 기반 NLP 라이브러리에 사용 제한은 없다.

### 429·재시도

429는 `HcxErrorType.RATE_LIMIT` → `ServiceUnavailableException` → 503으로 나간다. 주최측이 5xx에
재시도 2회를 하지만 「429로 답변에 실패해도 구제하지 않는다」가 공지 내용이므로 우리 쪽에서 먼저 막는다.

`RetryingHcxClient`가 한 곳에서 재시도를 맡는다(Spring AI 안쪽 재시도는 꺼 둔다).

- 다시 거는 것: `RATE_LIMIT`(429) · `TIMEOUT` · `UPSTREAM`(5xx)
- 즉시 실패: `AUTHENTICATION` · `CONFIGURATION` · `BAD_REQUEST`(429가 아닌 4xx) ·
  `INVALID_RESPONSE` — 다시 걸어도 같다
- `INVALID_RESPONSE`는 **모델이 빈 텍스트를 준 경우만**이다. 끊긴 연결은 `TIMEOUT`,
  읽을 수 없는 응답 본문은 `UPSTREAM`이 되어 둘 다 재시도된다
- 대기는 1초에서 2배씩, 한 번에 최대 8초. `Retry-After` 헤더가 있으면 그 값을 따른다
- 총 대기 예산 120초. 서버가 큰 `Retry-After`를 줘도 예산을 넘길 대기는 하지 않고 실패한다

최악의 경우에도 시도 3회 × 호출 타임아웃 30초 + 대기 예산 120초 = **210초**로 평가 타임아웃
300초 안이다. 기본 백오프만 쓰면 대기는 1초 + 2초뿐이다.

재시도를 다 써도 실패하면 503으로 나간다. 근거를 찾았는데 문장만 못 만든 것을 답변 불가로
내보내면 시스템 실패를 정상 답변으로 위장하는 것이라 그렇게 하지 않는다
(`docs/data-model.md` §9와 같은 이유).

### `maxTokens` 실측 (2026-09-04, HCX-005, 질문 11개)

TPM은 `input token + maxTokens`로 계산되므로 상한을 낮추면 한도에 덜 닿는다. 다만 잘린 답은
틀린 답이라 바닥을 실제로 재고 정했다. 절차와 표는 `backend/README.md`「출력 길이 측정」에 있다.

- 출력 최대 **377토큰** — 현대건설 `20230626800002`. 코퍼스에서 정정 사슬이 가장 길다(14회)
- 출력 평균 143토큰 · 입력 최대 1,696토큰
- 같은 질문 재호출 시 출력이 최대 1.6배까지 흔들림
- → 최댓값의 두 배인 **768**로 정함. 건당 TPM이 최악 2,720 → 2,464로 줄어든다

기본값은 `HcxProperties`와 `application.yml` 두 곳에 있고 실제로 뜨는 값은 yml이 정한다.
어긋나도 스프링 컨텍스트로는 잡히지 않는다. `src/test/resources/application.yml`이 운영 설정을
가려서 테스트가 운영 yml을 아예 읽지 못하기 때문이다. `HcxConfigurationTest`가 파일을 직접
읽어 둘을 묶어 둔다.
