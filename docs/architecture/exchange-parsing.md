# 거래소공시 파싱 설계

거래소공시 1,469건 전수 조사를 근거로 한 설계다. 구현은
`preprocess/chaltteok_etl/exchange/krx_forms.py`.

## 1. 목적

한국거래소 수시공시에서 계약·투자 금액과 기간을 근거와 함께 뽑아, 단일조회와
비교계산 질문에 답할 수 있게 한다.

## 2. 원문은 HTML이다 — DART XML 파서를 재사용할 수 없다

확장자는 `.xml`이지만 1,469건 전부 루트 태그가 `<html>`이다.

| | 정기공시·주요사항보고서 | 거래소공시 |
|---|---|---|
| 포맷 | DART 고유 XML (`DOCUMENT>BODY>SECTION-1`) | HTML (`<html><body><div class="xforms">`) |
| 항목 식별 | `ACODE` 속성 | **없음 — 라벨 텍스트로 식별** |
| 값 셀 | `<TE ACODE="...">` | `<span class="xforms_input">` |

값 셀 표시는 일관돼서, 1,469건 전부에서 라벨-값 쌍을 1개 이상 뽑았다(쌍 0건 없음).

### charset 선언을 믿지 않는다

`<meta charset=euc-kr>`이 1,469건 전부에 있으나 **실제 바이트는 1,469건 전부 UTF-8**이다.
선언대로 디코딩하면 한글이 전부 깨져 라벨을 하나도 찾지 못한다. UTF-8로 고정해 읽는다.

## 3. 서식은 4종뿐

`report_nm`은 136종이지만 `[기재정정]` 접두와 괄호 부제(`(자율공시)`,
`(CT-P42 임상 3상 결과 발표)`)를 떼면 4종이다.

| 서식 | 건수 | 사실 | 근거 chunk |
|---|---:|:---:|:---:|
| 단일판매ㆍ공급계약체결 | 1,106 | ○ | ○ |
| 투자판단관련주요경영사항 | 300 | ✗ | ○ |
| 신규시설투자등 | 43 | ○ | ○ |
| 단일판매ㆍ공급계약해지 | 20 | ○ | ○ |

### 투자판단관련주요경영사항에서 사실을 만들지 않는 이유

`1. 제목` / `2. 주요내용` 두 칸이 전부이고, 주요내용이 중앙값 457자(최대 2,640자)
자유 서술이다. 금액 문자열이 있는 문서는 300건 중 79건뿐이고 그마저
`5.9조원 (※ 美상무부 보조금 0.7조원 포함)`처럼 단위가 섞이고 단서가 붙는다.
숫자만 뽑으면 보조금 포함 여부가 사라져 **근거와 어긋나는 값을 확정하게 된다.**

근거 chunk는 만드므로 "어떤 투자를 했나" 같은 질문에는 원문을 근거로 답한다.
계산·비교가 필요한 질문만 나머지 3종 1,169건(79.6%)이 대상이다.

## 4. 항목 식별 — 라벨 키에 대단원을 반영한다

번호가 붙은 라벨(`3. 계약상대방`)은 대단원을 열고, 글머리가 붙은 라벨
(`-최근 매출액(원)`)은 직전 대단원에 속한다. 키는 `대단원>항목`으로 만든다.

### ⚠️ 글머리만 떼면 서로 다른 회사의 매출이 섞인다

조건부 계약 서식에는 자사 `최근 매출액(원)`과, 「3. 계약상대방」 하위의
`-최근 매출액(원)`(상대방 매출)이 함께 있다. 글머리를 떼고 공백만 지우면 두 라벨이
같은 키가 되어 한 문서에 `contract_recent_revenue`가 두 개 생긴다.

레인보우로보틱스 `20240315900173`이 실제 사례다. 자사 매출 13,615,411,936원(136억)과
계약상대 한국항공우주산업 2,786,888,282,702원(2.7조)이 섞여, 매출을 **200배 틀리게**
답할 수 있었다. 상대방 매출은 `contract_counterparty_recent_revenue`로 분리한다.

### 공백은 지운다

같은 항목이 서식마다 공백이 다르다 — `최근매출액(원)` / `최근 매출액(원)`.

### 별칭

| 라벨 | fact_key | 비고 |
|---|---|---|
| `계약상대` / `계약상대방` | `contract_counterparty` | 조건부 서식 26건이 후자 |
| `계약금액(원)` / `계약금액총액(원)` | `contract_amount` | 조건부 서식은 총액 행이 대응 |
| `계약(수주)일자` / `계약(수주)일` | `contract_order_date` | 1,048건 / 58건 |

## 5. 단위 — 라벨이 아니라 서식 표에 상수로 둔다

값이 원문에서 이미 정규화되어 있다. 금액은 원 고정, 날짜는 ISO 고정이라
정기공시처럼 표 단위로 단위 스코프를 관리할 필요가 없다.

단위를 라벨에서 뽑지 않는 이유는 조건부 계약 서식의 `확정 계약금액`처럼 라벨에
단위 표기가 없는 항목이 있어서다. 라벨에서 뽑으면 같은 금액이 서식에 따라 단위가
있고 없고가 갈린다. 서식 표에 `raw_unit`/`normalized_unit`을 명시한다.

날짜는 3종 형식을 받는다 — `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY년 M월 D일`.

## 6. 값이 `-`이면 사실을 만들지 않는다

계약금액이 `-`인 64건 중 63건은 유보사유가 `경영상 비밀유지`다. 파싱 실패가 아니라
**정상적으로 값이 없는 문서**이므로 추측하지 않고 사실을 생략한다
(주요사항보고서의 `-` 처리와 같다).

## 7. 기간 기준과 연결·별도

거래소공시는 사건 공시다. 값은 접수 시점의 상태를 가리키므로 전 사실이
`period_basis = point_in_time`, `as_of_date = rcept_dt`다. 재무제표가 아니라서
`scope = not_applicable`이다.

## 8. 정정본

정정본 563건(50.9%). `2. 정정관련 공시서류제출일`이 원본 접수일을 가리킨다.
`(기업, 제출일)`로 원본을 찾으면 212건이 1건으로 특정되고, **242건은 원본이
2023-01-01 이전이라 코퍼스에 없다.** 이는 결함이 아니다.

정정본을 독립 문서로 적재하고, 답변할 때 같은 계약이면 최신 정정본이 원본을
대체한다(주요사항보고서와 같은 원칙).

## 9. 적용 범위

전량 실행 결과 **1,469건 전부 성공, 실패 0건**. 근거 17,600 / 사실 11,060,
추출 상태는 전부 `ok`다. 한 문서에 같은 `fact_key`가 두 번 나오는 문서는 없다.
