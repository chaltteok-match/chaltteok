# Chaltteok 공시 AI Agent 프로젝트 계획

- 문서 상태: Accepted
- MVP 개발 기간: 2026.08.03 ~ 2026.09.05
- 예선 제출 마감: 2026.09.06

## 1. 프로젝트 목표

### MVP

제공된 공시 데이터에서 질문과 관련된 문서를 검색하고, 정보를 추출·비교·계산하거나 정정·후속 공시를 추적한 뒤 HyperCLOVA X를 통해 근거와 정보 한계가 포함된 답변을 제공하는 평가 API를 구현한다.

### 장기 목표

대회 제출 이후 프론트엔드·백엔드·AI 기능을 연결해 실제 사용 가능한 근거 기반 공시 리서치 서비스로 확장한다.

- 자연어 공시 질의와 근거 확인
- 여러 기업·연도의 수치 비교
- 계약·투자·지분 변동 타임라인
- 관심 기업의 중요 공시와 변경사항 추적
- 분석 결과 저장 및 리포트 생성

## 2. 개발 원칙

### 세로 흐름 단위로 구현한다

공통 기반을 제외한 기능은 기술 계층별로 나누지 않는다. 각자는 담당 공시 유형에 대해 다음 흐름을 끝까지 구현한다.

```text
Python 공시 전처리
→ PostgreSQL 저장
→ 검색·계산·이력 판단
→ Spring Boot 서비스
→ HyperCLOVA X 연동
→ /answer API 응답
→ 자동 테스트
```

### 공통 기능은 중복 구현하지 않는다

다음 기능은 한 번만 만들고 문서와 PR 리뷰를 통해 공유한다.

- 평가용 `/answer` API와 요청·응답 모델
- 공시 및 근거 공통 모델
- 정정·후속공시 관계 모델
- HyperCLOVA X 클라이언트
- 환경변수와 공통 오류 응답
- PostgreSQL 연결과 Docker Compose

공통 모델은 담당자가 목적, 필드, 타입, 필수 여부, JSON 예시를 문서로 먼저 제안한다. 상대방의 비동기 리뷰를 반영한 후 Java와 Python 모델을 구현한다.

## 3. 기술 스택과 결정

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 언어 | Java 21 | 평가 API와 주요 애플리케이션 로직 |
| 백엔드 | Spring Boot | REST API, 질문 처리, 검색·계산·이력 추적 |
| AI 연동 | Spring AI | HyperCLOVA X 호출과 프롬프트 구성 |
| AI 연동 대안 | Spring RestClient | Spring AI 호환 문제 발생 시 직접 호출 |
| 데이터 처리 | Python 3.12 | XML·HTML·표 파싱과 데이터 정규화 |
| 데이터베이스 | PostgreSQL | 기업·공시·추출 정보·관계 저장 |
| 데이터 접근 | Spring Data JPA | 공시 메타데이터와 관계 데이터 조회 |
| 벡터 검색 | pgvector | 키워드 검색 한계가 확인될 경우 추가 |
| 테스트 | JUnit 5, Spring Boot Test, pytest | Java·Python 자동 테스트 |
| 실행환경 | Docker, Docker Compose | API와 DB 실행환경 통일 |
| 협업 | GitHub PR, GitHub Actions | 코드 리뷰와 자동 테스트 |

주요 결정은 다음과 같다.

- 외부 평가 API는 Spring Boot 하나로 제공한다.
- Python은 API 서버가 아닌 전처리 프로그램으로 사용한다.
- Spring과 Python을 마이크로서비스로 분리하지 않는다.
- 2인·1개월 MVP에 맞춰 하나의 모노레포와 모듈형 단일 애플리케이션을 사용한다.
- 검색은 메타데이터·키워드 기반으로 먼저 구현한다.
- pgvector는 검색 성능 부족이 확인된 경우에만 추가한다.
- HCX는 Spring AI의 OpenAI 호환 클라이언트로 연동한다(`SpringAiHcxClient`).

## 4. 시스템 구조

```text
제공 공시 데이터
      ↓
Python 전처리
- 문서 파싱
- 문장·표·수치 추출
- 공시별 정보 정규화
      ↓
PostgreSQL
- 공시 메타데이터
- 추출 문장과 수치
- 정정·후속공시 관계
      ↓
Spring Boot
- 질문 유형 분류
- 관련 공시 검색
- 비교·계산
- 이력 및 최종 상태 판단
- HyperCLOVA X 호출
      ↓
근거가 포함된 /answer 응답
```

질문 처리 로직은 HTTP 계층과 분리한다.

```text
GET /answer
      ↓
AnswerHandlerSelector
      ├── ExchangeAnswerHandler
      ├── FundraisingAnswerHandler
      ├── FinancialAnswerHandler
      └── (지분공시 Handler)
      ↓
AnswerService
      ↓
AnswerResult
```

컨트롤러는 입력을 받고 `AnswerService`를 호출한 뒤 평가 API 형식으로 변환하는 역할만 담당한다.

## 6. MVP 범위와 역할 분담

공시 유형 네 가지를 두 사람이 두 개씩 담당한다. 단일 조회와 답변 불가는 모든 공시 유형에 적용하고, 비교·계산과 이력 추적은 공시 특성에 맞게 배분한다.

| 담당 | 공시 유형 | 공통 기능 | 심화 기능 |
| --- | --- | --- | --- |
| 예령 | 정기공시 | 단일 조회·답변 불가 | 비교·계산 |
| 예령 | 거래소공시 | 단일 조회·답변 불가 | 계약·투자 이력 추적 |
| 다은 | 주요사항보고서 | 단일 조회·답변 불가 | 종합·비교·계산 및 조건 변경 추적 |
| 다은 | 지분공시 | 단일 조회·답변 불가 | 지분 변화 이력 추적 |

작업은 세 페이즈로 나눈다. 순서는 우선순위이지 차단선이 아니다.
페이즈1이 끝나야 페이즈2를 시작할 수 있는 것은 아니고, **담당이 다르면 겹쳐서 진행한다.**
지분공시(페이즈1)를 기다리느라 손익 구멍·429·라우팅 검증(페이즈2)을 미루지 않는다.
페이즈3은 기능 동결이 전제라 앞 두 페이즈가 끝난 뒤에 시작한다.

주최측이 정한 제출·평가 조건은 [평가 요구사항](evaluation-requirements.md)에 따로 둔다.

### 페이즈1 · 네 유형 연결

공시 유형마다 Python 전처리 → DB → 검색 → HCX → `/answer`를 한 벌로 잇는다.

| 작업 | 담당 | 상태 |
| --- | --- | --- |
| 공통 기반 — `/answer`, DTO, DB, HCX 클라이언트, CI | 공동 | 완료 |
| 정기공시 — 요약재무정보 파싱, 연결·별도 구분, 연도 비교·증감률 | 예령 | 완료 |
| 주요사항보고서 — 유상증자결정 파싱, 목적별 금액과 합계 | 다은 | 완료 |
| 거래소공시 — 계약·투자 파싱, 정정 이력 추적 | 예령 | 완료 |
| 지분공시 — 대량보유상황보고서 파싱, 보유자·수량·지분율 단일 조회 | 다은 | 완료 |

적재 현황은 정기공시 1,021건, 거래소공시 1,469건, 주요사항보고서 55건, 지분공시 0건이다.

지분공시 단일 조회는 대량보유상황보고서의 보유자·보유 수량·지분율까지 연결했다.
아직 하지 않은 것은 다음과 같다.

- 신규·변경·해소 보고 연결
- 보유 목적 및 시점별 변화 판단

### 페이즈2 · 정확도 개선

연결이 끝난 유형부터 손본다. 지분공시를 기다리지 않는다.

| 작업 | 담당 | 상태 |
| --- | --- | --- |
| `/answer` 라우팅 검증 — Handler 넷이 한 애플리케이션에서 질문을 서로 뺏지 않는지 | 예령 | 미착수 |
| 라이브 테스트 종단 재구성 — 손으로 쓴 문구 대신 Handler가 만든 문구로 검증 | 예령 | 미착수 |
| 유상증자 목적 제외 규칙 — `타법인 증권취득자금을 제외한 총액` 같은 질문 | 다은 | 완료 |
| 유상증자 신주·발행가·액면가 조회 | 다은 | 완료 |
| 유상증자 포함+제외 동시 질문 — `시설자금을 포함하고 타법인 증권취득을 제외한 총액`처럼 둘 다 나온 질문. 제외에 붙은 목적만 뺀다 | 다은 | 완료 |
| 주요사항보고서 유형 확대 — 자기주식취득결정 예정 주식·금액 | 다은 | 완료 |
| 주요사항보고서 유형 확대 — CB·BW·EB·시설투자 | 다은 | 미착수 |
| 지분공시 이력 — 신규·변경·해소 보고를 한 사건으로 잇기 | 다은 | 미착수 |
| 정기공시 기업 간 비교 | 예령 | 미착수 |
| 답변 불가 범위 확대 — 데이터 밖 질문, 미래 예측·투자 의견, 프롬프트 공격 | 공동 | 미착수 |

## 7. 정정·후속공시 관계

정정공시는 별도 공시 유형이 아니라 기존 공시와 연결되는 관계로 처리한다.

공통 관계 구조에서 다음 정보를 관리한다.

- 원본 공시 ID
- 후속 또는 정정 공시 ID
- 관련 기업과 사건 식별자
- 공시일과 관계 유형
- 변경 전·후 상태와 최종 상태

공통 관계 구조는 문서와 PR로 함께 검토하고, 실제 연결 규칙과 검증은 각자의 담당 흐름에 적용한다.

- 예령: 계약·투자 변경 및 해지
- 다은: 자금조달 조건 변경 및 지분 변동

## 8. 작업 및 리뷰 규칙

Issue·브랜치·PR 이름과 세부 리뷰·병합 방식은 [협업 가이드](../CONTRIBUTING.md)를 따른다.

```text
담당자 초안 작성
→ Issue 또는 문서로 공유
→ 상대방 비동기 의견
→ 담당자 반영 및 구현
→ Pull Request
→ 상대방 실행·리뷰
→ 승인 후 main 병합
```

- `main`에 직접 푸시하지 않는다.
- 최신 `main`에서 목적별 브랜치를 생성한다.
- 모든 작업은 PR을 통해 병합한다.
- 공통 기반 PR은 의존 순서대로 병합한다.
- 기능 PR은 수정 영역이 겹치지 않으면 병렬로 진행한다.
- 리뷰어는 가능하면 로컬에서 실행한다.
- 작업은 실행, 테스트, 환경변수·문서 반영까지 완료해야 종료한다.

## 10. MVP 이후 확장

단순 챗봇이 아니라 답변, 근거 문서, 수치 비교, 변경 이력을 함께 보여주는 공시 리서치 워크스페이스로 확장한다.

- 근거 기반 공시 챗봇
- 기업·연도별 비교 차트
- 계약·투자 및 지분 변동 타임라인
- 관심 기업의 신규·정정 공시 알림
- 분석 결과 저장과 근거 기반 리포트

현재는 확장 가능한 경계만 유지한다.

- 검색·계산·LLM 로직을 컨트롤러에 작성하지 않는다.
- `AnswerService`를 HTTP 요청 형식과 분리한다.
- 평가 API DTO와 내부 답변 모델을 분리한다.
- 답변 근거를 구조화된 목록으로 관리한다.
- 공시 유형별 Handler를 독립적으로 테스트한다.

```text
현재: GET /answer ──┐
                    ↓
               AnswerService
                    ↓
                AnswerResult

추후: POST /chat ───┤
      비교 API ──────┤
      타임라인 API ──┤
      리포트 API ────┘
```

프론트엔드와 사용자·대화·알림 기능은 MVP 제출 이후 별도 단계에서 구현한다.
